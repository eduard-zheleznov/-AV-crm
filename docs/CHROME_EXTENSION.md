# Chrome в режиме инкогнито без Playwright

Режим `chrome_extension` использует установленный Google Chrome. По умолчанию каждая
управляемая вкладка создаётся только в окне инкогнито. Python не запускает Chrome через
Playwright, WebDriver или remote debugging. Расширение выполняет только одну текущую команду
локального загрузчика: открыть объявление, нажать кнопку телефона с не более чем
одним ограниченным повтором, вернуть
DOM-номер либо снимок активной вкладки для локального OCR.

Версия приложения `1.12.44` требует расширение `1.0.20`. Эти две части обновляются
вместе; несовпадение версий блокирует запуск до чтения первой строки.

`AVITO_EXTENSION_INCOGNITO=true` включает обязательный режим инкогнито. Если Chrome не дал
расширению доступ к инкогнито, контекст вкладки не совпал или Chrome не смог создать
окно, запуск завершается с технической ошибкой до обработки очереди. Автоматического fallback в
обычную вкладку нет.

## Безопасность

- мост слушает только `127.0.0.1` и недоступен из локальной сети;
- каждый компьютер получает случайный 256-битный токен;
- токен хранится только в локальных `.env` и `chrome-extension/config.local.js`;
- `config.local.js` исключён из Git;
- расширение имеет доступ только к `avito.ru` и локальному мосту;
- каждая managed tab проверяется по признаку `incognito`; обычная вкладка не переиспользуется;
- разрешение `debugger` используется только на время одного coordinate-free
  `Runtime.evaluate` с `userGesture:true` в текущей managed tab и всегда снимается
  в `finally`;
- разрешение `scripting` используется только как однократный fallback на уже
  committed Avito surface, когда static content script не отвечает; `about:blank`,
  чужой домен и другое объявление gate не проходят;
- одновременно выполняется только одна команда;
- CRM не затрагивается командой `avito-extension-test`.
- диагностический журнал `logs/chrome-extension-health.jsonl` содержит только
  технические признаки и публичный числовой ID объявления; полные URL, телефоны,
  токены и содержимое страницы туда не записываются.

## Health probe и самовосстановление

Перед первым объявлением загрузчик выполняет startup canary: расширение открывает
домашнюю поверхность Avito и подтверждает, что content script видит отрисованный DOM.
Canary не нажимает кнопку телефона, не меняет очередь и не обращается к CRM.

Для каждой навигации готовность определяется по отрисованному DOM, а не только по
событию Chrome `status=complete`. Каноническая смена slug разрешена, если числовой
ID объявления совпадает. Переход на другой ID классифицируется как неверная ссылка,
а зависание tab/renderer/content script — как `browser_infra`.

Пока Chrome сообщает `pendingUrl`, расширение не делает probe, reload или injection.
После commit ожидаемой Avito surface оно даёт static content script grace-период;
если receiver всё ещё отсутствует, `runtime-core.js` и `content.js` один раз
инжектируются через `chrome.scripting` только в main frame. Диагностика сохраняет
лишь классы surface (`about:blank`, `avito:root`, `avito:listing` и т. п.), без URL.

При `browser_infra` расширение действует ограниченно:

1. закрывает только собственную managed tab;
2. ждёт `AVITO_EXTENSION_RECOVERY_BACKOFF_SECONDS`;
3. создаёт новую managed tab и повторяет ту же строку один раз;
4. при повторной неудаче возвращает строку без расходования попытки телефона;
5. перед следующей строкой требует новый успешный canary, иначе останавливает run.

Открытый long-poll служит idle heartbeat расширения во время worker. Между
отдельными run состояние доказывается новым startup canary, а не старым heartbeat.
Если canary видит CAPTCHA или авторизацию, он не пытается их обходить и останавливает
начало очереди для ручного действия оператора.

В `1.0.18` listing не ждёт ненадёжных `tab.status=complete` и
`document.readyState=complete`: текущий Avito может оставаться `loading/interactive`
после фактической отрисовки. Вместо этого расширение требует совпадение
Avito ID, пустой `pendingUrl`, текущую версию content script и четыре
стабильных rendered-probe за не менее 1,5 с. Затем content script прокручивает
текущую reveal-кнопку в viewport и требует три стабильных измерения одного
DOM-элемента. React-замена сбрасывает счётчик, а неактивный дубль кнопки не
блокирует поиск следующей actionable-цели.
Затем service worker повторно проверяет command ID, managed tab ID, Avito ID и STOP,
подключает debugger и в одной MAIN-world evaluation с `userGesture:true` заново
находит текущую видимую кнопку и вызывает её `.click()`. Координаты экрана, фокус
omnibox, клавиатурные события и Windows SendInput не используются. После dispatch
расширение не считает
клик успешным, пока DOM не
подтвердил смену состояния: кнопка исчезла, появился phone DOM или новая
поверхность номера. Если эффекта нет, цель заново ищется и клик повторяется
ровно один раз. Повторный `click_not_effective` останавливает run без OCR и без
расходования попытки строки. OCR разрешается только после reveal confirmation.

В `1.0.13` после `chrome.debugger.attach` service worker сначала активирует renderer
через CDP `Page.bringToFront` и `Runtime.evaluate(window.focus())` с `userGesture`, чтобы
выбранный omnibox не перехватывал browser-level input. Затем координаты кнопки
получаются только после attach и
фокусировки managed tab. Content script заново ищет кнопку, прокручивает её,
проверяет hit target и возвращает центр в уже изменённом viewport. Service worker
повторно проверяет command/tab/listing/STOP непосредственно перед CDP input.
Координаты, измеренные до attach, не передаются и не используются.

В `1.0.14`, если mouse dispatch выполнен, но DOM reveal не подтверждён,
расширение допускает два различных bounded keyboard fallback: Enter, затем Space.
Перед каждым шагом выполняется новый attach/focus, re-query и hit-test той же
кнопки; keyboard event разрешён только если `document.activeElement` точно совпадает
с проверенной reveal-кнопкой. Перед keyDown повторно проверяются
command/tab/listing/STOP; keyUp гарантируется как cleanup. Synthetic `.click()` не используется.

## Установка

Закройте Chrome for Testing. Установленный Chrome Stable и обычный профиль не удаляются и не
изменяются: рабочие вкладки загрузчика будут жить в отдельном окне инкогнито.

```powershell
Set-ExecutionPolicy -Scope Process Bypass -Force
.\scripts\install-chrome-extension.ps1
```

Скрипт откроет `chrome://extensions` и папку расширения. В Chrome:

1. включите **Режим разработчика**;
2. нажмите **Загрузить распакованное расширение**;
3. выберите папку `chrome-extension` из проекта;
4. откройте **Сведения** для **Avito CRM Local Bridge**;
5. включите **Разрешить использование в режиме инкогнито**;
6. вернитесь к списку, нажмите **Обновить** и проверьте версию `1.0.20`.

После обновления файлов проекта нажмите **Обновить** на странице
`chrome://extensions` в режиме разработчика. Загрузчик проверяет версию расширения
и не начнёт обработку со старым сценарием.

После обновления `1.0.20` Chrome сохраняет разрешения `scripting` и `debugger`, но доступ к
инкогнито включается вручную на карточке расширения. Подтвердите разрешения только для
**Avito CRM Local Bridge** и перезапустите Chrome.
Один раз откройте `service worker` на
карточке расширения: Console должна быть без ошибок. Затем выполните только
операторский canary из следующего раздела; полноценный run до его успеха не запускайте.

Перезагрузка Windows не нужна. Не копируйте `config.local.js` на другие компьютеры.

## Первый тест без CRM

Используйте объявление, которое только что успешно проверено вручную в окне инкогнито этого же
Chrome. На первом тесте разрешён один клик:

```powershell
.\.venv\Scripts\python.exe -m avito_crm avito-extension-test `
  "https://www.avito.ru/..." --max-clicks 1
```

Расширение само откроет одну вкладку и выведет её на передний план. Успешный тест
должен вывести `Chrome UI-gesture отправлен`, затем `раскрытие номера подтверждено DOM`.
Если появляется `browser_click_unavailable`, `debugger_busy` или
`click_not_effective`, это NO-GO:
CRM не запускать. Если Avito
покажет капчу, загрузчик:

1. не перезагружает страницу;
2. выводит управляемое окно на передний план и ожидает ручного решения в этой же вкладке;
3. после перенаправления повторно проверяет Avito и продолжает ту же команду и строку;
4. ждёт без ограничения времени до решения капчи либо команды STOP.

Это одинаково работает как на предстартовой проверке, так и при обработке объявления.
Подробная таблица для сотрудника: [MANUAL_AVITO_CHECKS.md](MANUAL_AVITO_CHECKS.md).

После получения номера команда печатает его источник и завершается без Google
Sheets и LPTracker.

Инкогнито не использует cookies обычного профиля и удаляет сессию после закрытия всех окон
инкогнито. Если нужен вход в Avito, выполните его отдельно в открытом окне инкогнито и не
закрывайте его до завершения запуска. Капча по-прежнему решается только вручную.

Для восстановления после circuit-breaker сначала вручную перезапустите обычный
Chrome, обновите расширение и убедитесь, что Avito отрисовывается. Затем под
наблюдением оператора последовательно выполните два
`avito-extension-test --max-clicks 1` на ранее успешных разных объявлениях; второй
не запускается при ошибке первого. GO для production допустим только если оба
canary завершились, в журнале есть `healthy`, а вкладка не зависла. При CAPTCHA
оставьте её оператору; не обновляйте страницу серией повторов.

## Возврат к Playwright

Локально замените в `.env`:

```dotenv
AVITO_BROWSER_DRIVER=playwright
```

Токен и конфигурацию расширения можно оставить для будущей диагностики. Не
удаляйте `.env.before-extension`, пока новый режим не прошёл контрольный запуск.
